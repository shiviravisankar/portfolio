The Situation

SoraCloud is a platform for teams running AI workloads on their own GPU infrastructure. Orchestration, model training, and deployment sit in one console instead of three or four separate tools. The product has to work for two different people on the same screens: a startup CTO who wants to deploy a model without learning infrastructure, and a data science lead at a larger org who needs full visibility, cost control, and the ability to allocate resources across teams. I joined as sole UX designer for seven weeks, working with a senior visual designer who led the UI.

The Tension

Simplify the interface and the data science lead loses control they need. Show everything by default and the startup founder never gets past setup. Separate views for each type of user were not an option for a startup building one product on one timeline. The console had to work for both without splitting into two products.

The Decisions

One console, not two products

The client had already decided against siloed tools before I joined: orchestration, training, and deployment would live in one platform. That set the direction, but it also raised the actual design problem. One console still had to serve two people with opposite defaults, and role based views that showed each of them a separate app were not realistic for a team building a single product on a short timeline.

Depth on demand instead of asking who you are

Rather than ask a user to declare their experience level up front, I built every screen so that what someone chooses to open decides how much they see. Nobody is sorted into a role. A user who never touches an advanced option never has to think about it. A user who needs that control gets to it in a couple of clicks, on the same screen, without switching modes or products. This single principle, applied consistently, is what let one console hold both users.

Craft

Machine setup, reduced to one command. Adding a machine could have been a form asking for GPU specs, region, and cluster config. Instead it is a single install script with a token. Someone who already knows their infrastructure does not need to be walked through fields they could fill in blind.

Three levels of detail on one deploy screen. Simple mode has four fields. Advanced mode adds model and deployment parameters. Autoscaling sits behind its own checkbox inside Advanced, revealing instance counts and target utilization only once it's checked. Each level has to be opened on purpose.

A monitoring table that stays plain until there's a reason to act. By default it's a read only list. Filters narrow it as you use them. Move, drain, and remove don't appear as buttons until you select a row.

Assembled workflows, given a name instead of exposed parts. Recipes like PodScribe or AutoUnderwriter package a model plus retrieval plus whatever else is needed under one name and a short description, for someone who wants a working result on day one.

Outcome

This was a pre launch handoff for a startup still in stealth. There's no usage data or adoption numbers to share yet, and I'm not going to claim results that don't exist. What this case study shows is the design decisions and the screens they produced, not performance data.

Reflection

The client came in already wanting one unified console, so that decision was made before the project started. What was left to solve was how to build one interface for two users with opposite needs, without either of them feeling like an afterthought. The answer wasn't a single clever screen. It was applying the same principle, optional depth, consistently across setup, deployment, monitoring, and workflow selection.
